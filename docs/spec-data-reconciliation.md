# Spec: Data Reconciliation and Quality Monitor

Project 3 of the portfolio. Fictional client: Thornfield Retail Group, a multi-channel retailer whose data platform team runs this report as the morning check: did last night's loads land, does the warehouse match the source systems, and which breaks need chasing. All data is synthetic, generated by a committed deterministic script (Phase 2). This spec is the ground truth for the data generator, the semantic model and the report. Deviations found during build are written back here.

Design: `docs/design-reference-data-reconciliation.html`, set **3a** ("Control Room": deep slate canvas #14181F, dark cards #1C222B, cyan #58B7D4 reserved for data flow, green #57A773 / amber #D9A03F / red #D65F5F reserved strictly for pass / warn / fail, Segoe UI with tabular numerals). The figures in the mockups are illustrative; every number in the built report must trace to the generator output.

Status: **draft, awaiting Lorenzo's approval**. No code until approved.

## 1. Business scenario

Thornfield Retail Group trades through around 640 stores and a webshop. Every night a batch platform loads eight feeds from six source systems into the analytics warehouse. The data platform team (audience: engineers and analysts, not executives) opens this monitor each morning before the business opens its own dashboards.

The report answers four engineering questions, one per page, plus a drillthrough detail:

1. **Morning Check**: did last night's run land clean, and what needs attention today?
2. **Reconciliation**: does the warehouse match the source, feed by feed, pairwise?
3. **Quality Rules**: once the data is in, is it fit to use? The rulebook across the five quality dimensions.
4. **Break Register**: every unresolved discrepancy, owned and aged - the team's queue, judged as a process.
5. **Feed Detail**: one feed end to end (drillthrough target).

## 2. Reporting window and run date

| Item | Value |
|---|---|
| Data range | Nightly runs from **01 Apr 2026 to 29 Jun 2026** (90 nights) |
| Run date | **Mon 29 Jun 2026**, the latest completed run. The Run date slicer defaults to it |
| Trend windows | "Last 30 nights" and "last 14 nights" visuals are trailing windows ending at the selected run date |
| Default report view | Run date = 29 Jun 2026, Source system = All, Severity = All |

The published figures are deterministic because the Run date slicer defaults to a fixed date, exactly as projects 1 and 2 froze their as-at dates. Nothing keys off the system clock. Unlike project 2 (month grain), this project carries a proper **daily Date table**, marked as a date table: runs are nightly and the trailing-window measures need day arithmetic.

## 3. The core modelling decisions

Two decisions carry the project, and they are what it demonstrates:

1. **The facts are measurements about data, not the data itself.** The warehouse does not re-store 2.4 million POS rows; it stores that last night's POS extract had 2,412,384 rows at source and 2,412,384 rows landed, with matching amount totals. This is how real reconciliation monitors work (a metadata store), and it keeps the model honest: every headline figure is an aggregation of stored measurements.

2. **Verdicts are computed, never stored.** The generator writes raw observations (row counts, amount totals, rows failing a rule, minutes late). Pass / warn / fail is derived in DAX by comparing observations against the thresholds held on the Rule dimension. No upstream status flag is trusted; change a tolerance in the Rule table and every verdict, colour and KPI re-derives. Status colours come from a single conditional-format measure, so the traffic discipline (green = pass, amber = warn, red = fail, nothing else) is enforced in one place.

### Seeded narrative (the story the data must tell)

Targets for the Phase 2 generator. Exact values come from the generator; the spec fixes the shape and the 29 Jun landing figures:

- **29 Jun run: 4,654,459 source rows compared ("4.65m"), row match rate 99.97%** against the 99.90% threshold. Six feeds pass, one warns, one fails.
- **Supplier EDI invoices FAIL**: file 2 of 3 never arrived at the gateway. Warehouse 7,736 rows vs source 8,940 (**-1,204 rows**), amount 1,379,600 vs 1,594,208 (**-214,608**). The files that did arrive landed at 05:41 against the 05:00 window.
- **E-commerce orders WARN, third consecutive night**: -3 rows, -412 amount (0.039%, inside the 0.05% tolerance). Root cause in the register: refund-timing between the webshop and the warehouse.
- **The 14 Jun incident**: a truncated POS extract dropped the match rate to ~98.9% (roughly 51k rows short) and spiked failing records to ~61k. Raised, resolved next day, and still visible in every 30-night trend - the monitor's job is to remember.
- **Supplier EDI is the repeat offender**: also failed 22 Jun (row count mismatch, break still open waiting on a supplier resend), warned 18 Jun, and owns 5 of the 14 open breaks.
- **Timeliness is the weak quality dimension** (~97.5% pass over 30 nights vs 99%+ elsewhere): Supplier EDI and Logistics shipments keep missing the 05:00 arrival window.
- **Breaks at 29 Jun: 14 open (3 critical, 4 high, 7 lower)**, oldest is BRK-0171, product master schema drift, 9 days old. Median open age ~3 days. **MTTR ~2.1 days against a 3.0-day target**; last 7 nights resolved 11 vs opened 9. Steady-state elsewhere: loyalty email validity ~0.67% failing (inside its 1% tolerance), product master carries 14 duplicate barcodes (warn against a zero-tolerance rule).
- All other feed-nights pass quietly: the board should be mostly green, because a monitor that is always red teaches people to ignore it.

## 5. Star schema

```
Date 1--* Feed Run     *--1 Feed
Date 1--* Check Result *--1 Feed
                       *--1 Rule
Date 1--* Break        *--1 Feed
     (active: Opened Date; inactive: Resolved Date, activated by measure)
```

Three dimensions (Date, Feed, Rule) and three facts (Feed Run, Check Result, Break). All relationships single-direction, many-to-one from fact to dimension. One deliberate inactive relationship: Break to Date on Resolved Date, activated with USERELATIONSHIP inside the resolution-flow measures (the same pattern project 1 used for actions). Source system is an attribute of Feed, not a separate table: it is a property of the feed, and a slicer on the column serves the design.

### 5.1 Date (dimension, daily)

Grain: one row per day, 01 Apr to 30 Jun 2026. Columns: `Date`, `DateKey` (int YYYYMMDD), `Day Label` ("29 Jun"), `Weekday` (Mon..Sun), `Is Weekend`, `Week Start` (Monday), `Month`. Marked as a date table.

### 5.2 Feed (dimension)

Grain: one row per monitored feed. Columns: `FeedKey`, `Feed`, `Source System`, `Schedule` (Daily / Weekdays / Mon-Sat), `Steward`, `Has Amount` (bool), `Arrival Deadline` ("05:00"). Eight rows per the table above.

### 5.3 Rule (dimension)

Grain: one row per quality rule. 48 rows: each feed carries between 4 and 9 rules, covering reconciliation-style checks (row count vs source, amount vs source, arrival) and in-warehouse checks, all classified into the **five quality dimensions**: Completeness, Validity, Uniqueness, Timeliness, Consistency.

| Column | Notes |
|---|---|
| `RuleKey` | surrogate |
| `Rule Id` | stable, quotable: "R-001" ... "R-048" |
| `Rule Name` | plain words: "invoice count vs manifest", "email format valid" |
| `FeedKey` | the feed the rule runs against (also carried on the fact) |
| `Quality Dimension` | Completeness / Validity / Uniqueness / Timeliness / Consistency |
| `Tolerance Label` | the human-readable tolerance shown in visuals: "0", "&le; 1%", "05:00" |
| `Warn Above %` | fail rate above which the verdict is at least WARN (usually 0) |
| `Fail Above %` | fail rate above which the verdict is FAIL |
| `Warn Late Mins` / `Fail Late Mins` | timeliness rules only: minutes past the deadline for WARN / FAIL |

Anchor rules named in the design (the generator fills the rest of the 48 with sensible coverage): R-003 POS basket total equals line sum (Consistency, zero tolerance, always passing); R-008 e-commerce customer id present (Completeness, warn >0, fail >0.5%); R-011 GL debits equal credits (Consistency, zero, passing); R-014 loyalty email format (Validity, warn >0.25%, fail >1%); R-017 supplier EDI file lands by 05:00 (Timeliness, warn >0 min, fail >60 min or absent); R-019 supplier EDI invoice count vs manifest (Completeness, warn >0, fail >0.5%); R-021 product master barcode unique (Uniqueness, warn >0, fail >0.05%).

The row-count and amount reconciliations are themselves rules (Completeness and Consistency respectively) with warn/fail thresholds matching the tolerances stated on the report: **row counts exact (warn above zero, fail above 0.5%), amounts within &plusmn;0.05%**.

### 5.4 Feed Run (fact)

Grain: **one row per feed per scheduled night.** No row on a no-run night.

| Column | Type | Notes |
|---|---|---|
| `DateKey` | int | FK to Date (the run night) |
| `FeedKey` | int | FK to Feed |
| `Source Rows` | int | rows in the source extract |
| `Warehouse Rows` | int | rows landed in the warehouse |
| `Source Amount` | decimal | blank for non-monetary feeds (W6) |
| `Warehouse Amount` | decimal | blank for non-monetary feeds |
| `Arrival Time` | text "HH:MM" | when the last expected file landed; blank if a file never arrived |
| `Files Expected` / `Files Received` | int | the missing-file story is visible in the raw data |

No status column: the verdict is derived (section 3).

### 5.5 Check Result (fact)

Grain: **one row per rule per scheduled night** (from the rule's first active date, see W3).

| Column | Type | Notes |
|---|---|---|
| `DateKey` | int | FK to Date |
| `RuleKey` | int | FK to Rule |
| `FeedKey` | int | FK to Feed (denormalised for direct feed slicing) |
| `Rows Checked` | int | denominator |
| `Rows Failed` | int | numerator; 0 is stored, not blank - zero means zero |
| `Minutes Late` | int | timeliness rules only; blank otherwise. Blank plus files missing = FAIL by rule logic |

### 5.6 Break (fact / register)

Grain: **one row per discrepancy raised.** Register-style, like project 1's actions.

| Column | Type | Notes |
|---|---|---|
| `Break Id` | text | "BRK-0158" ... stable, quotable |
| `Opened DateKey` | int | FK to Date (active relationship) |
| `Resolved DateKey` | int | FK to Date (inactive relationship); blank while open |
| `FeedKey` | int | FK to Feed |
| `Category` | text | Missing file / Row count mismatch / Amount mismatch / Late arrival / Schema drift / Duplicate keys |
| `Severity` | text | Critical / High / Medium / Low (sorted by a hidden key) |
| `Owner` | text | the steward names |
| `Status` | text | plain words: Investigating, Root cause identified, Waiting on supplier resend, Fix scheduled, Change raised with ERP team, Resolved |

## 6. Measure catalogue

Business definitions are binding; exact DAX is Phase 3. Counts format with thousands separators; rates to two decimal places for match rate and one for pass rates; deltas always signed. Ratios return BLANK when the denominator is empty. "Selected night" = the Run date slicer value; trailing windows end at it.

### Reconciliation (Feed Run fact)

| # | Measure | Business definition |
|---|---|---|
| 1 | Source Rows | Sum of source rows in context |
| 2 | Warehouse Rows | Sum of warehouse rows |
| 3 | Row Delta | Warehouse Rows minus Source Rows, signed |
| 4 | Rows Reconciled | Source Rows on the selected night (the "4.65m" KPI) |
| 5 | Row Match Rate % | 1 minus (sum of absolute row deltas / Source Rows). 99.90% threshold stated on the card |
| 6 | Source Amount / Warehouse Amount / Amount Delta | As rows 1-3 for the monetary feeds; BLANK (rendered as a dash) for non-monetary feeds |
| 7 | Amount Delta % | Amount Delta / absolute Source Amount |

### Verdicts (derived, never stored)

| # | Measure | Business definition |
|---|---|---|
| 8 | Check Verdict | For a rule-night in context: FAIL if fail rate exceeds `Fail Above %` (or minutes late exceed `Fail Late Mins`, or an expected file is absent); WARN if above the warn threshold; PASS otherwise; "No run" when no result row exists |
| 9 | Feed Verdict | Worst Check Verdict across the feed's rules that night (fail > warn > pass) |
| 10 | Feeds Passing / Warning / Failing | Count of scheduled feeds by Feed Verdict on the selected night (the "6 / 8" KPI) |
| 11 | Verdict Colour | Returns the hex for the verdict (#57A773 / #D9A03F / #D65F5F / neutral). The single conditional-format measure behind every status chip, tile and grid cell |

### Quality rules (Check Result fact)

| # | Measure | Business definition |
|---|---|---|
| 12 | Rules Evaluated | Distinct rules with a result on the selected night |
| 13 | Rules Passing / Warning / Failing | Split of 12 by Check Verdict |
| 14 | Rows Checked / Rows Failing | Sums in context |
| 15 | Fail Rate % | Rows Failing / Rows Checked |
| 16 | Dimension Pass Rate % | Share of rule-night evaluations with verdict PASS over the trailing 30 nights, by quality dimension. Denominator = evaluations, not nights x rules (W3) |
| 17 | Failing Records Trend | Rows Failing per night over the trailing 30 nights (the incident-memory line) |

### Breaks (register)

Open/closed state is always judged **as at the selected run date**: a break is open on date D if Opened <= D and (Resolved is blank or Resolved > D). The register is time-travelling, not a snapshot.

| # | Measure | Business definition |
|---|---|---|
| 18 | Open Breaks | Count open as at the selected night (the alarm KPI) |
| 19 | Critical Open Breaks | Open Breaks with Severity = Critical |
| 20 | Break Age Days | Selected night minus Opened, per open break; drives the register Age column and the ageing buckets |
| 21 | Median Open Age | Median of 20 across open breaks |
| 22 | Oldest Open Break | Age and id of the oldest open break, for the KPI context line |
| 23 | Mean Time To Resolve | Mean of (Resolved minus Opened) for breaks resolved in the trailing 28 nights, via the inactive Resolved Date relationship. Target <= 3.0 days stated on the card. Excludes W5's invalid row |
| 24 | Resolved This Week / Opened This Week | Counts in the trailing 7 nights (resolved uses the inactive relationship) |
| 25 | Repeat Offender Feed | The feed carrying the most open breaks, for the KPI card |
| 26 | Invalid Break Records | Count of breaks with Resolved before Opened (W5): the monitor monitors itself |

## 7. Deliberate data-quality wrinkles

The wrinkles are meta this time: the defects live in the monitoring data itself, and the model visibly copes. Each is planted by the generator, documented in the generator README, and handled in the open.

| # | Wrinkle | Where | How the model handles it |
|---|---|---|---|
| W1 | No-run nights: ERP GL loads weekdays only, Supplier EDI Mon-Sat | run + check facts | Schedule-aware measures: a missing row on an unscheduled night renders as a neutral "No run" cell, never a failure, and stays out of every pass-rate denominator |
| W2 | The 14 Jun incident rerun wrote a second, corrected result set for POS that night, so raw check results contain duplicates for one feed-night | check results CSV | Deduplicated keep-latest on the natural key in a named Power Query step; row counts before/after noted in the README |
| W3 | Rule R-021 (barcode unique) was only added to the rulebook on 15 May, mid-window | check results | Pass-rate denominators count actual evaluations, not nights x rules, so the late rule does not depress history it was never part of |
| W4 | Arrival times in one source extract are recorded inconsistently ("05:41", "05:41:22", "5:41") | feed run CSV | Normalised to HH:MM in a named Power Query step; the raw column is preserved in the CSV so the cleaning is inspectable |
| W5 | One resolved break has Resolved before Opened (a data-entry slip) | break register CSV | Flagged by the Invalid Break Records measure, excluded from MTTR, and left visible in the register rather than silently fixed |
| W6 | Four feeds have no monetary measure | feed run CSV | Amount columns are genuinely blank (not zero); amount measures return BLANK and the report renders a dash - absence shown honestly |

## 8. Report pages

Canvas 1280x720, layout, palette and typography per design set 3a. Colour discipline: cyan #58B7D4 = data flow (volumes, trends); green / amber / red = pass / warn / fail only, driven by the single Verdict Colour measure. Same verdict, same colour, every page. Dark theme via the report theme JSON.

### Slicers (top-right, same order everywhere, synced)

| Slicer | Pages | Default |
|---|---|---|
| Run date | 1, 2, 3 | 29 Jun 2026 |
| Source system | 1, 2, 3, 4 | All |
| Severity | 1, 4 | All (page 3 swaps it for Quality dimension; page 4 leads with Status = Open) |

### Page 1: Morning Check

KPI band (5 cards): Rows reconciled, Row match rate % (vs stated 99.90% threshold, green when in tolerance), Feeds passing x/8, Open breaks (the red alarm card), Oldest open break. Visuals: feed status board (8 tiles, one per feed: verdict chip, rows, delta - the only red object is the failed feed); 30-night match-rate line against the dashed amber threshold with the 14 Jun dip annotated; open breaks by category; "what failed last night" table (feed, check, expected, got, delta, verdict chip).

### Page 2: Reconciliation

The pairwise proof. Full-width feed reconciliation table for the selected night: source rows / warehouse rows / row delta / source amount / warehouse amount / amount delta / verdict, tolerances stated in the card header, dashes for non-monetary feeds, zeros shown as zeros. Below, the signature move: the **check grid**, feed by night for the trailing 14 nights, one square per run (green / amber / red / neutral no-run). Right-click a row to drill through to Feed Detail.

### Page 3: Quality Rules

KPI band: rules evaluated, passing, warnings, failing. Pass rate by quality dimension (trailing 30 nights) as bars, the dragging dimension in amber; failing-records trend line with the 14 Jun spike annotated; rule results table, worst first (rule id and name, feed, dimension, rows checked, rows failing, fail rate, stated tolerance, verdict chip).

### Page 4: Break Register

KPI band: open breaks (alarm), median age, MTTR vs target, resolved-vs-opened this week, repeat-offender feed. Ageing buckets (red only on the over-7-days tail); open breaks by feed; the register (break id, opened, feed, category, severity chip, owner, status in plain words, age). Drillthrough to Feed Detail.

### Page 5: Feed Detail (drillthrough)

Drillthrough target on Feed, hidden from navigation; back button; filter pill. Header card: feed, source system, last-run verdict (left edge takes the verdict colour), pairwise rows, amount delta, steward. Visuals: paired columns source-beside-warehouse for the trailing 14 nights (warehouse bar red on failed nights, near-zero on no-run nights); the feed's checks for the selected night with verdict chips; the feed's open breaks with the same columns as the register.

## 9. Out of scope

- No live pipeline integration: the CSVs simulate the metadata store a real monitor would query. The generator stands in for the platform's control framework.
- No record-level payloads: the model stores measurements about the data, not the data (section 3). No drill-to-failing-row.
- No RLS, no incremental refresh, no composite models, no calculation groups: the showcase is the metadata-fact pattern, derived verdicts, the inactive-relationship break flow and the daily-grain trailing windows.
- No SLA/cost framing and no alerting simulation: the monitor reports; the fictional team acts.
